# Bâtir un orchestrateur Claude Code piloté par messagerie

Pour un développeur solo sur Pro, la voie la plus mince, la plus conforme et la moins chère est **un orchestrateur maison**. Il tient en une session Claude Code interactive sous tmux avec le plugin officiel Channels (Telegram ou Discord), les workers sont lancés avec `claude --bg` dans des worktrees automatiques, la file d'attente vit dans les labels d'issues GitHub, et le plafond de concurrence est imposé par un script. Aucun projet open source examiné ne combine pilotage entrant par messagerie, file plafonnée et lien avec les issues GitHub : l'assemblage reste à faire, et même l'outil dédié le plus avancé (Agent Orchestrator) n'a pas de plafond fiable. Le vrai goulet n'est pas la génération mais la revue, et sur Pro la bande passante d'abonnement : les sources convergent pour dire que 1 à 2 workers actifs est le régime tenable, ce qui rend le plafond de 2 (3 pour les tâches légères) déjà ambitieux. Côté facturation, la scission annoncée le 15 juin 2026 (Agent SDK, `claude -p`, GitHub Actions basculés sur un crédit mensuel à tarif API) a été **suspendue le jour même et n'est pas appliquée à ce jour**, mais Anthropic dit la retravailler : il faut donc concevoir en mode interactif natif pour rester insensible à un retour. Côté sécurité, un bot de messagerie relié à un shell réunit les trois jambes de la « lethal trifecta » ; les contrôles prioritaires sont l'allowlist d'expéditeur, des identifiants GitHub sans pouvoir de fusion, un sandbox avec liste d'hôtes autorisés, et un kill switch hors bande. Le dispositif Cordeau (protection de `main`, reviewer, `needs-human`) couvre déjà l'essentiel du risque de fusion ; il reste à écrire un ADR avec section Implications sécurité avant tout code, et à avancer par paliers, en commençant par un mode lecture seule.

## Les briques officielles couvrent déjà 80 % du besoin

Anthropic fournit désormais presque toutes les pièces, toutes disponibles sur Pro et alimentées par le même pool d'abonnement. Channels (Telegram, Discord, iMessage, en research preview) pousse les messages dans une session `claude` interactive ; les utilisateurs Pro/Max sans organisation sautent les contrôles d'administration et activent le plugin par session avec `--channels`, mais les événements n'arrivent que tant que la session est ouverte, d'où la nécessité d'un process persistant ([docs Channels](https://code.claude.com/docs/en/channels)). Seuls les plugins de l'allowlist Anthropic sont acceptés pendant la preview, le flag est absent de `claude --help` et sa syntaxe peut changer ([docs Channels](https://code.claude.com/docs/en/channels)). Remote Control pilote une session locale depuis l'app mobile, exige que la machine reste allumée, propose `--spawn worktree` et `--capacity`, et n'accepte pas les clés API ([docs Remote Control](https://code.claude.com/docs/en/remote-control)). Agent View (`claude agents`, `claude --bg`, `claude agents --json`, `claude stop|attach|logs`) déplace automatiquement chaque session de fond dans un worktree sous `.claude/worktrees/`, pousse les commits et ouvre une PR en brouillon à la fin, sans jamais forcer-pousser ni fusionner sur `main` ; il n'a **aucun plafond de concurrence** et chaque session consomme le quota indépendamment ([docs Agent View](https://code.claude.com/docs/en/agent-view)). Les sessions cloud (`claude --cloud`) déchargent le Mac, partagent les mêmes limites de compte et n'ajoutent aucun coût de VM ([docs sessions cloud](https://code.claude.com/docs/en/claude-code-on-the-web)). Les routines (`/schedule`) tirent sur l'abonnement comme une session interactive, avec un intervalle cron minimal d'une heure et 100 exécutions planifiées par heure et par compte ([docs routines](https://code.claude.com/docs/en/routines)). Enfin « Claude Code in Slack » fonctionne sur Pro/Max (une session cloud par @mention dans un canal, GitHub uniquement), alors que Claude Tag, l'identité partagée d'organisation, n'existe pas sur les plans individuels ([docs Slack](https://code.claude.com/docs/en/slack)).

Les agent teams, eux, sont un mauvais choix ici : expérimentaux, désactivés par défaut, sans reprise des teammates en cours, un seul team par session, et la doc recommande de commencer par de la recherche et de la revue plutôt que de l'implémentation parallèle ([docs agent teams](https://code.claude.com/docs/en/agent-teams)). Leur surcoût est de l'ordre de 7 fois les tokens d'une session standard avec des teammates en plan mode ([docs coûts](https://code.claude.com/docs/en/costs)), et Anthropic indique que les systèmes multi-agents consomment environ 15 fois les tokens d'un chat, ce qui ne se justifie que pour des tâches à forte valeur ([Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)). La hiérarchie officielle va du plus léger au plus lourd : sous-agents, sessions manuelles en worktrees, cloud, puis agent teams ([docs agent teams](https://code.claude.com/docs/en/agent-teams)). Le choix pour Cordeau suit la même gradation.

## Aucun projet open source ne livre l'assemblage complet

Le seul dépôt qui marie Channels, orchestrateur-agent et tmux est `Aitensity/claude-agent-fleet`, mais c'est un squelette : **0 étoile, un seul commit du 12 juin 2026**, aucun push depuis ([API GitHub](https://api.github.com/repos/Aitensity/claude-agent-fleet)). Il vaut comme patron d'architecture, pas comme dépendance : un agent par session tmux, une boucle de respawn `while true; claude; sleep 5`, un `CLAUDE_CONFIG_DIR` isolé par agent, le token de bot dans le Keychain, et un `CLAUDE.md` qui sert de cerveau à l'orchestrateur ([README](https://github.com/Aitensity/claude-agent-fleet), [architecture.md](https://github.com/Aitensity/claude-agent-fleet/blob/main/docs/architecture.md)). Il n'offre ni file, ni plafond, ni worktrees, ni lien avec les issues.

Les grandes plateformes sont très actives mais larges, et chargées d'issues ouvertes. Oh-my-claudecode (39 579 étoiles, MIT) lance `omc team N:claude` en panneaux tmux, avec N choisi à l'appel plutôt qu'un plafond global, et n'offre que des notifications sortantes vers Telegram/Discord/Slack ([README](https://github.com/Yeachan-Heo/oh-my-claudecode)). Agent Orchestrator (12 737 étoiles, Apache-2.0, 755 issues ouvertes) est le plus proche du flux Cordeau : branche et worktree par worker, suivi de PR, de CI et de revue, intake d'issues GitHub en lecture seule, Kanban jusqu'à « Ready to merge » ([README AO](https://github.com/Untrivial-ai/agent-orchestrator)). Mais son plafond `maxConcurrentSessions` n'a pas été porté dans la réécriture Go (PR #918 fermée sans fusion), et une issue d'août 2026 rapporte un orchestrateur mort après 40 à 45 workers sur un Mac de 8 Go ([issue #3921](https://github.com/Untrivial-ai/agent-orchestrator/issues/3921)). Ses interactions de merge n'ont pas été vérifiées, ce qui pose une question directe face à la règle « Claude ne fusionne jamais ». Paseo (19 488 étoiles) et Superset (14 865 étoiles, licence Elastic 2.0, non OSI) sont des clients riches mais sans messagerie ni plafond ; Paseo s'appuie sur l'Agent SDK (donc exposé à un retour de la facturation programmatique) ([package.json](https://github.com/getpaseo/paseo/blob/main/packages/server/package.json)), et Superset affiche des plantages du service hôte sous charge ([issue #7426](https://github.com/superset-sh/superset/issues/7426)). Ccpm (8 399 étoiles, dernier push mars 2026) transforme PRD en epic puis en issues GitHub, un cadre lourd qui double ce que fait déjà le repo ([README](https://github.com/automazeio/ccpm)). Worktrunk (8 790 étoiles) se limite à la gestion de worktrees sans file ni plafond ([README](https://github.com/max-sixty/worktrunk)), et Crystal est déprécié depuis février 2026 ([README](https://github.com/stravu/crystal)).

Pour la messagerie seule, il existe des bots Telegram (`overwirehq/claude-code-telegram`, 2 798 étoiles, SDK en voie principale avec repli CLI, webhooks GitHub signés HMAC) ([README](https://github.com/overwirehq/claude-code-telegram)), Discord et WhatsApp de maturité faible, et des clients mobiles dédiés comme Happy (24 009 étoiles, chiffrement de bout en bout) ([README](https://github.com/slopus/happy)) qui ne sont pas des messageries. cc-haha accepte Telegram, Slack et d'autres en messages privés, mais l'application de bureau doit rester ouverte et l'IM n'y est qu'une télécommande ([docs IM](https://github.com/NanmiCoder/cc-haha/blob/main/docs/im/index.md)). Le tableau suivant résume la lecture pour le besoin Cordeau.

| Option | Messagerie entrante | Plafond de concurrence | Lien issues/PR | Verdict |
|---|---|---|---|---|
| Channels + tmux + script maison | oui (officiel) | à écrire | `gh` déjà en place | **retenue** |
| claude-agent-fleet | oui (Channels) | non | non | patron à copier |
| Agent Orchestrator | notifications seules | non fiable | oui | option de supervision, phase tardive |
| oh-my-claudecode | sortante seulement | N à l'appel | non | non nécessaire |
| Paseo / Superset | non / Slack incertain | non | partiel | écartés (SDK, charge) |
| ccpm | non | non | oui, mais lourd | écarté |

## Le plafond, la file et le budget sont des invariants à écrire soi-même

Puisque ni Agent View ni les projets examinés ne bornent la concurrence, l'orchestrateur doit la faire respecter. Le design minimal que les notes tirent des sources est le suivant : l'orchestrateur compte les sessions en cours (`claude agents --json`, dont les champs d'état n'ont pas été confirmés) et refuse d'en démarrer une troisième, ou une quatrième légère. La file d'attente tient dans des labels d'issues GitHub (par exemple `agent:ready`, `agent:running`), plus durables qu'un fichier local parce qu'ils survivent aux crashs et se lisent depuis le téléphone, avec un `STATE.md` en miroir dans l'esprit de loop-engineering. Cette dernière recommandation est une inférence de conception, aucune source n'a comparé les deux. Le pattern d'escalade de loop-engineering convient bien : niveau 1 en rapport seul la première semaine, niveau 2 assisté, niveau 3 sans surveillance seulement après sept jours de précision démontrée, avec cet avertissement que « les boucles non surveillées font des erreurs non surveillées » ([loop-engineering](https://github.com/cobusgreyling/loop-engineering)).

Le budget est le contrainte dure sur Pro. L'usage suit une fenêtre glissante de cinq heures et une fenêtre hebdomadaire, partagées entre claude.ai, Desktop et Claude Code, et les quotas absolus ne sont pas publiés ([tarifs](https://claude.com/pricing), [limites](https://support.claude.com/en/articles/11647753-how-do-usage-and-length-limits-work), [erreurs](https://code.claude.com/docs/en/errors)). Chaque sous-agent ou session renvoie son propre contexte complet à chaque requête, et les tâches planifiées ou les messages inter-sessions rejouent le contexte même au repos ([docs coûts](https://code.claude.com/docs/en/costs)). Un guide d'agrégateur place Max 5x comme plancher des usages parallèles soutenus ([TrueFoundry](https://www.truefoundry.com/blog/claude-code-limits-explained)) ; l'extrapolation des notes, non mesurée, est qu'un Pro ne tient guère plus de 1 à 2 workers actifs durablement. Le seul signal programmatique documenté est le JSON de statusline, qui expose `rate_limits.five_hour` et `seven_day` avec `used_percentage` pour les abonnés ([docs statusline](https://code.claude.com/docs/en/statusline)). Un script de statusline peut écrire ces valeurs dans un fichier que l'orchestrateur lit avant de dispatcher, avec des seuils à calibrer (les notes proposent 80 % de la fenêtre de 5 h et 70 % de la semaine). Le schéma exact n'a pas été lu en entier. Au plafond, il faut attendre, changer de famille de modèle, ou activer l'usage supplémentaire par opt-in explicite ; la version 2.1.234 sait attendre puis reprendre seule (`autoContinueAtUsageLimit`) ([docs coûts](https://code.claude.com/docs/en/costs)). Piège de facturation à ne pas oublier : une variable `ANTHROPIC_API_KEY` dans l'environnement prend le pas sur l'abonnement et déclenche des frais API inattendus ([support](https://support.claude.com/en/articles/11145838-using-claude-code-with-your-pro-or-max-plan)).

Pour éviter les conflits de merge sur le monorepo, la règle déduite de la consigne d'Anthropic « chaque teammate possède ses fichiers » est un worker au plus par application (api, web, mobile) ou par bounded context, et la sérialisation de tout ce qui touche `packages/shared`, les lockfiles ou le contrat OpenAPI généré. Cela rejoint un constat répété : trois instances parallèles n'ont pas augmenté la production fusionnée parce que l'approbateur était le goulet ([Hack-Log](https://note.com/hacklog_stealth/n/n15572ab2f1f0?hl=en)), et Simon Willison ne peut « revoir et intégrer qu'un seul changement significatif à la fois » ([Willison](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)). La conséquence pratique est d'ajouter une limite de WIP sur les PR ouvertes (3, par exemple) en plus du plafond d'agents ; le reviewer Claude et l'auto-merge de Cordeau absorbent déjà une partie de ce goulet, sauf pour les PR `needs-human`.

## La facturation du 15 juin n'a pas eu lieu, mais le risque de retour demeure

Annoncé le 13 mai 2026, le plan sortait l'Agent SDK, `claude -p`, GitHub Actions et les applications tierces des pools d'abonnement vers un crédit mensuel séparé (Pro 20 $, Max 5x 100 $, Max 20x 200 $), au tarif API et sans report, tandis que le Claude Code interactif, le chat et Cowork restaient hors périmètre ([Help Center](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan), [digitalapplied](https://www.digitalapplied.com/blog/anthropic-claude-credit-overhaul-june-15-2026)). Le jour prévu, Anthropic a suspendu le changement : l'article indique que l'Agent SDK, `claude -p` et les apps tierces « tirent toujours sur les limites de votre abonnement » et que des mises à jour seront publiées avant tout changement ([Help Center](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan), [The New Stack](https://thenewstack.io/anthropic-pauses-claude-agent-sdk-subscription-change/)). Aucune source postérieure à juin n'annonce de nouvelle date ; un blog secondaire confirme le statu quo en septembre ([koromo.io](https://koromo.io/en/blog/claude-agent-sdk-credit-guide/)). Le README de claude-agent-fleet, qui date du 12 juin, présente donc comme acquise une mesure qui n'a jamais pris effet. Limite de ces notes : le Help Center n'a pas été relu directement avec sa date de mise à jour, et il faut le re-vérifier avant d'engager le design.

Pour les conditions d'utilisation, les Conditions Consommateur interdisent l'accès « par des moyens automatisés ou non humains, par bot, script ou autre », sauf par clé API ou « là où nous le permettons explicitement » ([Consumer Terms](https://www.anthropic.com/legal/consumer-terms), texte obtenu via un résumeur, à revérifier). La page légale de Claude Code précise que les limites annoncées supposent un « usage ordinaire et individuel », que l'OAuth est destiné aux acheteurs d'abonnements et à l'usage ordinaire des applications natives, et que les développeurs qui construisent des produits doivent utiliser des clés API ([légal et conformité](https://code.claude.com/docs/en/legal-and-compliance)). Aucun plafond de sessions simultanées n'a été trouvé, et les fonctions documentées (Channels, Remote Control, routines, GitHub Action avec jeton OAuth) sont explicitement permises. Mon analyse : un développeur qui pilote ses propres instances natives sur son propre matériel pour son propre travail est dans le périmètre, avec un risque d'interprétation sur le mot « ordinaire » pour du 24 h/24 parallèle. Deux lignes rouges se dégagent : ne jamais ouvrir le bot à une autre personne (clause de partage de compte), et ne pas faire passer un `claude -p` ou un Agent SDK pour une infrastructure de service. L'affirmation « abonnement = usage local uniquement, clé API sur serveur distant » vient de l'auteur d'Aitensity, pas d'un texte officiel. Un Mac dédié reste de l'usage personnel sur matériel propre.

## Un bot de messagerie relié à un shell exige des contrôles en couches

Le modèle de menace est la « lethal trifecta » : données privées, contenu non fiable, canal de sortie. Willison rappelle qu'on ne sait pas la prévenir à 100 % et qu'après ingestion d'une entrée non fiable l'agent doit être contraint de sorte qu'elle ne puisse déclencher aucune action conséquente ([Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). Le cas réel est connu : une issue malveillante dans un dépôt public a fait lire des dépôts privés à un agent via le MCP GitHub officiel ([Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability)). Pour Cordeau, les données privées sont le dépôt, les `.env` et les identifiants `gh` ; le contenu non fiable est constitué des corps d'issues, commentaires de PR, pages web et paquets tiers ; la sortie passe par `curl`, `git push`, les commentaires `gh` et les réponses du canal. Casser au moins une jambe est l'objectif, et les trois peuvent l'être à peu de frais.

Au niveau du canal, chaque plugin Channels garde une allowlist d'expéditeurs et ignore silencieusement les autres, avec appairage par code (`/telegram:access pair`, puis `policy allowlist`) ; si le canal relaie les permissions, toute personne pouvant y répondre peut approuver des outils, donc il ne faut autoriser que soi-même ([docs Channels](https://code.claude.com/docs/en/channels)). L'allowlist doit porter sur l'identité de l'expéditeur, jamais sur un salon (source secondaire : [claudefa.st](https://claudefa.st/blog/guide/development/claude-code-channels)). Le compte Telegram ou Discord du propriétaire équivaut à un accès shell en mode bypass, et les sources ne donnent pas d'autre parade que la double authentification ; les bots ne sont pas chiffrés de bout en bout, donc aucun secret ne doit transiter par le chat. Pour les secrets, le patron d'Aitensity place les tokens dans le Keychain, lus à l'exécution dans la boucle de respawn, avec répertoires de config en `chmod 700`, tout en admettant que la valeur reste dans l'environnement du process et que seule une règle du `CLAUDE.md` interdit sa lecture ([security.md](https://github.com/Aitensity/claude-agent-fleet/blob/main/docs/security.md)). Une consigne dans un prompt n'est pas un sandbox.

Côté exécution, Anthropic réserve `bypassPermissions` aux conteneurs et VM isolés ; le sandbox natif (Seatbelt sur macOS) borne le réseau à une liste d'hôtes autorisés ([modes de permission](https://code.claude.com/docs/en/permission-modes), [sandboxing](https://code.claude.com/docs/en/sandboxing)). Un Mac toujours allumé n'est pas isolé, donc mon jugement est de préférer le mode `auto` avec sandbox et liste d'hôtes réduite à github.com, aux registres de paquets et à l'API Anthropic, et d'exécuter les workers sous un utilisateur macOS dédié, voire dans un conteneur. Pour GitHub, un jeton fine-grained limité à ce dépôt, avec écriture sur les branches non protégées et sur les pull requests, sans admin ni contournement de protection, s'articule avec les règles existantes : `main` protégée, PR et CI obligatoires, `needs-human` pour `.claude/`, `CODEOWNERS` et le workflow du reviewer. Une PR ne peut donc pas réécrire son propre contrôle. Cette configuration de jeton n'a pas été vérifiée dans la documentation GitHub. Enfin, seules les issues rédigées par le propriétaire (login ou `author_association`) doivent être dispatchées ; les contenus externes et Dependabot ne sont jamais passés bruts à un worker. Le kill switch doit exister hors de l'orchestrateur : commande `/stop-all` via `claude stop`, plus un chemin hors bande (SSH/Tailscale pour tuer tmux, révocation du jeton GitHub, réinitialisation du token du bot), car un orchestrateur compromis ne peut pas être celui qui se coupe.

## Le Mac dédié multiplie les pièges opérationnels

L'expérience d'Aitensity est la source la plus détaillée, avec des symptômes vécus. `claude --channels` se fige lorsqu'il est lancé en headless par launchd (processus à environ 0 % de CPU, environ 7 descripteurs de fichiers contre plus de 30 sains), et la parade est une session tmux détachée ([pitfalls.md](https://github.com/Aitensity/claude-agent-fleet/blob/main/docs/pitfalls.md)). Les tickets cités (#37878, #9026) sont fermés, mais #37878 décrit un plantage de `claude -p` sous launchd, un symptôme voisin et pas forcément identique ([issue #37878](https://github.com/anthropics/claude-code/issues/37878)) ; à retester avec la version courante. Autres pièges : le TCC de macOS bloque silencieusement `~/Documents`, `~/Desktop` et `~/Downloads` pour les process headless ; une limite de 256 descripteurs fait planter `claude` au démarrage (`ulimit -n 65536` dans la boucle) ; les dialogues de premier lancement (confiance du dossier, plugins) bloquent les démarrages invisibles et doivent être préremplis ; Homebrew est absent du PATH des shells non interactifs ; `--continue` ne doit être ajouté que si une session existe, sinon la boucle plante ; l'injection de prompt dans le TUI par tmux est fragile (`send-keys Enter` ne valide pas) ([pitfalls.md](https://github.com/Aitensity/claude-agent-fleet/blob/main/docs/pitfalls.md)).

Le plugin Discord mérite une attention particulière : l'issue ouverte #3140 documente l'absence de garde de reconnexion, qui épuise le quota de 1 000 IDENTIFY par 24 h et conduit Discord à réinitialiser le token du bot ([claude-plugins-official#3140](https://github.com/anthropics/claude-plugins-official/issues/3140)). La boucle de respawn à pause fixe de 5 s peut aggraver cela ; elle doit donc reculer progressivement. D'autres signalements restent à l'état de simples extraits de recherche (messages entrants non livrés #38166, arrêt après la première réponse #36477, déconnexion permanente de Remote Control après limite de débit avec plusieurs sessions #32642). Comme la maturité de Discord et celle de Telegram diffèrent peu dans les sources, le choix du canal doit se faire par test : Telegram évite le piège IDENTIFY de Discord, mais cette préférence reste une hypothèse non démontrée.

Pour garder le Mac éveillé, les guides tiers recommandent `pmset` (sommeil désactivé, redémarrage automatique) plutôt que `caffeinate` seul, l'Ethernet filaire, Tailscale pour l'accès distant, et une prise HDMI factice pour un mini sans écran ; ces consignes proviennent d'extraits d'agrégateurs, diffèrent entre elles et n'ont pas été comparées à la documentation Apple ([MindStudio](https://www.mindstudio.ai/blog/keep-claude-code-agent-running-24-7), [guydevops](https://guydevops.com/posts/always-on-claude-code-remote-control-mac-mini/)). Les sessions Agent View survivent à la veille mais s'arrêtent à l'extinction, et les processus inactifs s'arrêtent après environ une heure puis reprennent depuis la transcription ([docs Agent View](https://code.claude.com/docs/en/agent-view)). Une expiration de la connexion claude.ai demande un nouveau `/login` manuel, ce qui fait de la supervision hors bande une exigence. L'auto-login après redémarrage compromet FileVault, un arbitrage non traité par les sources.

## Recommandation phasée pour Cordeau

Le principe directeur est d'écrire d'abord la décision, puis de livrer par paliers où chaque niveau d'autonomie se gagne sur preuve, conformément à la règle de la maison : ADR avant le code.

La phase 0 est documentaire et ne touche aucun code. Elle consiste à rédiger l'ADR « Orchestrateur de flotte d'agents piloté par messagerie » dans `docs/adr/` avec sa section Implications sécurité obligatoire (surface d'attaque ajoutée par le bot, secrets manipulés, absence de données personnelles dans le canal, points de fuite), à mettre à jour l'index des ADR, et à y inscrire les invariants : plafond de 2 workers (3 s'ils sont légers), un worker par application, limite de WIP sur les PR ouvertes, seules les issues du propriétaire dispatchées, jeton GitHub sans pouvoir de fusion. L'ADR doit aussi trancher la question de facturation en précisant que le design reste interactif natif et que `claude -p` n'est qu'un usage ponctuel, avec une revérification du Help Center à une date inscrite. Comme l'ADR et la configuration `.claude/` du Mac touchent la racine de confiance, toute PR sur `.claude/` est `needs-human` et fusionnée par le fondateur. Cette phase inclut aussi un test de faisabilité de 30 minutes sur le Mac une fois reçu : `claude --channels` dans tmux, mesure des descripteurs de fichiers, comportement après redémarrage.

La phase 1 installe la plomberie en rapport seul (niveau 1). Elle comprend un utilisateur macOS dédié, `pmset`, Tailscale, une session tmux avec boucle de respawn à recul exponentiel, le plugin Channels Telegram (ou Discord) en allowlist sur son seul compte, le token en Keychain, et le dépôt hors des dossiers protégés par TCC. L'orchestrateur ne fait qu'une chose : lire les issues, résumer l'état (`claude agents --json`, `gh`), répondre aux commandes de statut, d'arrêt et de budget. Il ne lance aucun worker. Critère de sortie : une semaine sans plantage non récupéré, un kill switch hors bande testé (SSH, révocation du jeton, reset du token du bot).

La phase 2 active un seul worker assisté (niveau 2). L'orchestrateur lance `claude --bg --name feat-<n> --model <m> "<prompt pointant l'issue n>"` pour une issue du propriétaire étiquetée `agent:ready`, sur la branche `feat/<n>-<slug>` dans un worktree automatique, en mode `auto` avec sandbox et hôtes autorisés. Le worker ouvre sa PR, et le circuit existant fait le reste : CI, reviewer Claude, auto-merge ou `needs-human`. Le prompt rappelle les règles du repo (TDD, `/simplify` avant la PR, audit système de test pour un `fix:` hors dev local), et la commande de fusion reste interdite. Le script de dispatch lit le fichier de budget issu de la statusline et refuse de démarrer au-delà des seuils. Les tâches à faible coût (docs, dépendances, petites corrections) vont à Sonnet ou Haiku.

La phase 3 passe à deux workers en parallèle, sur deux applications différentes, avec la limite de WIP sur les PR. Le troisième worker n'est autorisé que pour une tâche légère. Cette phase suit sept jours de précision démontrée en phase 2, et se juge sur trois mesures : part des PR fusionnées sans reprise, consommation de la fenêtre de 5 h et du budget hebdomadaire, nombre de PR `needs-human`. Si la fenêtre de 5 h sature régulièrement, la réponse est de réduire à un seul worker ou de passer à Max 5x (100 $), pas de relever le plafond. Les routines `/schedule` et les sessions cloud sont une option pour des tâches périodiques à faible volume (triage, balayage de dépendances), en gardant à l'esprit que l'intervalle minimal est d'une heure et qu'elles consomment le même pool.

La phase 4, optionnelle, évalue la supervision visuelle. Agent Orchestrator et Paseo ne se justifient que si la lecture de `claude agents` et des PR depuis le téléphone devient insuffisante ; ni l'un ni l'autre ne doit être adopté avant d'avoir vérifié qu'il ne peut pas fusionner de PR et qu'il respecte le plafond. Les agent teams restent exclus, sauf pour une exploration en lecture seule ponctuelle.

## Conclusion

Le résultat le plus utile de cette recherche est négatif : il n'existe pas de produit clé en main pour ce besoin, et ce vide est moins un manque qu'une indication. Les briques officielles (Channels, Agent View, worktrees automatiques) sont solides, les projets tiers sont soit trop jeunes, soit trop larges, et la vraie valeur de l'orchestrateur tient en trois invariants que nul outil ne garantit : un plafond de concurrence, un budget lisible, et une chaîne de confiance qui interdit toute fusion par l'agent. Cordeau possède déjà les deux tiers de ce dispositif (protection de `main`, reviewer, `needs-human`), si bien que l'orchestrateur n'ajoute qu'une porte d'entrée et un répartiteur, et que l'essentiel du travail porte sur la sécurité de cette porte.

Deux risques restent hors de contrôle et justifient la progression par paliers : la politique de facturation, qu'Anthropic dit retravailler sans calendrier, et la maturité du plugin Channels, encore en research preview avec des défauts connus. Inscrire dans l'ADR une date de revérification de ces deux points, et ne passer à un niveau d'autonomie supérieur qu'après des preuves chiffrées sur l'usage d'abonnement, vaut mieux que de maximiser le débit : sur Pro, le facteur limitant est de toute façon le quota, et sur la revue.

Limites de ces notes : aucun test d'exécution réel n'a été fait, les quotas absolus de Pro et de Max ne sont pas publiés, les consignes d'alimentation du Mac viennent de guides tiers non recoupés avec la documentation Apple, et le texte exact des Conditions Consommateur et la date de mise à jour du Help Center sont à revérifier à la source.
