# Alternatives comparées : quelle stack offre une « robustesse agent-friendly » pour un SaaS métier ? Ce qui est propre à Rust, et ce qui vient de n'importe quel typage statique fort avec une boucle de feedback rapide

> Notes de recherche, rédigées le 2026-10-01. Périmètre : le backend de Cordeau et la logique métier partagée. Candidats comparés : Rust (Axum/SQLx), TypeScript strict de bout en bout (+ Effect-TS), Go, Kotlin (Ktor/Spring, KMP), Gleam/OCaml/F#/Elixir, et le statu quo PHP 8.5 durci.
> Convention : chaque fait est sourcé en ligne. Les déductions personnelles sont rangées dans « Inferences », et ce qui n'a pas pu être vérifié dans « Gaps ».

---

## Q1 — Quelle fraction des classes de bugs typiques du code généré par LLM est bloquée à la compilation, et par quelle stack ?

### Takeaway

Les deux études quantitatives disponibles se complètent. Environ **94 % des erreurs de compilation** du code TypeScript généré par LLM sont des erreurs de typage. En revanche, environ **30 % seulement des bugs** du code LLM (taxonomie de Tambon et al.) relèvent de catégories qu'un vérificateur de types attrape à coup sûr. Environ 25 % sont attrapables _en partie_ par des garanties « fortes » (null-safety, matching exhaustif, erreurs comme valeurs), et environ 45 % sont des bugs fonctionnels qu'aucun système de types n'attrape. La valeur qui distingue Rust des autres se joue presque entièrement dans cette tranche « partielle ». Or Kotlin, OCaml/F#/Gleam et, en bonne partie, TS strict partagent ces garanties.

### Cited Findings

**Études sur la détection de bugs par le typage**

- Gao, Bird et Barr (ICSE 2017) : Flow 0.30 et TypeScript 2.0 détectent chacun **15 % des bugs publics** de projets JavaScript. Méthode : ajout manuel d'annotations sur le code bogué, puis vérification que le checker lève une erreur. — [Gao et al., ICSE 2017 (PDF Microsoft Research)](https://www.microsoft.com/en-us/research/wp-content/uploads/2017/09/gao2017javascript.pdf) ; [It Will Never Work in Theory](https://neverworkintheory.org/2021/09/08/to-type-or-not-to-type.html)
- Bogner et Merkel (MSR 2022) contredisent en partie ce résultat par fouille de dépôts GitHub : le ratio de commits de correction de bugs est **plus élevé** dans les projets TypeScript (0,206) que dans les projets JavaScript (0,126), et le délai de correction n'y est pas plus court. Les auteurs concluent que TS « does not automatically lead to fewer and easier-to-fix bugs ». — [Bogner & Merkel, arXiv 2203.11115](https://arxiv.org/pdf/2203.11115)
- Mündler, He, Wang, Sen, Song et Vechev (« Type-Constrained Code Generation with Language Models », PLDI 2025) : dans le code TypeScript généré par LLM, **94 % des erreurs de compilation** viennent d'échecs de vérification de types, contre 6 % d'erreurs syntaxiques. Le décodage contraint par les types réduit les erreurs de compilation de **74,8 %** (contre 9,0 % pour une simple contrainte syntaxique) et améliore la correction fonctionnelle de 3,5 à 5,5 % en relatif. Modèles testés : 2B à 34B paramètres. — [arXiv 2504.09246](https://arxiv.org/pdf/2504.09246) ; [ACM DL](https://dl.acm.org/doi/10.1145/3729274)
- GitHub Octoverse 2025 reprend ce chiffre de 94 % (« Type systems reduce ambiguity and catch LLM errors before production ») et l'utilise pour expliquer que TypeScript soit passé n°1 sur GitHub en août 2025 en nombre de contributeurs (+1 054 015 contributeurs, +66,6 % sur un an). — [GitHub Blog, Octoverse 2025](https://github.blog/news-insights/octoverse/octoverse-a-new-developer-joins-github-every-second-as-ai-leads-typescript-to-1/)

**Taxonomies des bugs du code LLM**

- Tambon et al. (EMSE 2025) : 333 bugs dans du **Python** généré par CodeGen, PanGu-Coder et Codex (dataset CoderEval). Répartition : Misinterpretation 20,77 %, Missing Corner Case 15,27 %, Hallucinated Object 9,57 %, Incomplete Generation 9,57 %, Silly Mistake 9,57 %, Wrong Attribute 8,55 %, Non-Prompted Consideration 8,15 %, Prompt-biased Code 6,52 %, Syntax Error 6,11 %, Wrong Input Type 5,91 %. Les modèles plus forts (Codex) font **davantage** de Missing Corner Case (23,5 %). — [Tambon et al., arXiv 2403.08937](https://arxiv.org/html/2403.08937) ; [Springer EMSE](https://link.springer.com/article/10.1007/s10664-025-10614-4)
- Wang et al. (« What's Wrong with Your Code Generated by LLMs? », 2024 ; Python ; 9 LLM dont GPT-4, Claude 3, DeepSeek-R1) : les bugs **fonctionnels** dominent, et d'autant plus que le problème est complexe (plus de 60 % sur APPS+ Competition pour la plupart des modèles). Les bugs syntaxiques restent rares (moins de 5 %). L'API misuse est l'erreur d'exécution la plus fréquente. Les vérifications de cas limites manquantes pèsent environ 54 % des erreurs logiques sur HumanEval+. — [arXiv 2407.06153](https://arxiv.org/html/2407.06153)

**Garanties à la compilation, candidat par candidat (documentation officielle)**

- **Rust** :
  - pas de `null` (`Option<T>`) et erreurs comme valeurs (`Result<T, E>`, opérateur `?`) — [The Rust Book ch. 9](https://doc.rust-lang.org/book/ch09-00-error-handling.html) ;
  - `Result` est `#[must_use]`, donc ignorer un résultat déclenche un avertissement — [std::result](https://doc.rust-lang.org/std/result/) ;
  - `match` exhaustif — [Rust Book ch. 6.2](https://doc.rust-lang.org/book/ch06-02-match.html) ;
  - immutabilité par défaut (`let` / `let mut`) — [Rust Book ch. 3.1](https://doc.rust-lang.org/book/ch03-01-variables-and-mutability.html) ;
  - « Safe Rust guarantees an absence of data races » via `Send`/`Sync`, **mais pas** l'absence de race conditions en général (deadlocks, courses logiques) — [Rustonomicon, Data Races](https://doc.rust-lang.org/nomicon/races.html) ;
  - SQLx vérifie les requêtes SQL brutes contre le schéma de la base **à la compilation** — [launchbadge/sqlx](https://github.com/launchbadge/sqlx).
- **TypeScript strict** :
  - `strictNullChecks` — [TSConfig strictNullChecks](https://www.typescriptlang.org/tsconfig/#strictNullChecks) ;
  - `noUncheckedIndexedAccess` — [TSConfig](https://www.typescriptlang.org/tsconfig/#noUncheckedIndexedAccess) ;
  - unions discriminées avec exhaustivité via `never` — [Handbook, Narrowing/exhaustiveness](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#exhaustiveness-checking) — ou via une règle de lint — [typescript-eslint switch-exhaustiveness-check](https://typescript-eslint.io/rules/switch-exhaustiveness-check/) ;
  - le système de types est **volontairement non sûr** (« unsound ») en plusieurs points — [Handbook, A Note on Soundness](https://www.typescriptlang.org/docs/handbook/type-compatibility.html#a-note-on-soundness).
- **Go** :
  - pas de types somme (« Why does Go not have variant types? ») — [Go FAQ](https://go.dev/doc/faq#variant_types) ;
  - piège de l'interface `nil` non égale à `nil` — [Go FAQ, nil error](https://go.dev/doc/faq#nil_error) ;
  - les data races sont détectées **à l'exécution** par `-race`, pas à la compilation — [Go race detector](https://go.dev/doc/articles/race_detector).
- **Kotlin** :
  - null-safety intégrée au système de types — [Kotlin docs, Null safety](https://kotlinlang.org/docs/null-safety.html) ;
  - classes `sealed` avec `when` exhaustif — [Kotlin docs, Sealed classes](https://kotlinlang.org/docs/sealed-classes.html).
- **PHP durci** (voir Q8) : PHPStan niveau 10 vérifie « everything it knows how to check », y compris l'usage de `mixed` — [PHPStan Rule Levels](https://phpstan.org/user-guide/rule-levels). Les génériques passent par PHPDoc et non par le langage — [PHPStan, Generics in PHP using PHPDocs](https://phpstan.org/blog/generics-in-php-using-phpdocs).

### Inferences

- **Projection de la taxonomie de Tambon sur les garanties statiques** (estimation personnelle, sur du Python et des modèles de 2023 — à prendre comme un ordre de grandeur) :
  - _Attrapé par tout typage statique digne de ce nom_ (attributs et objets vérifiés, arguments typés) : Syntax 6,1 + Wrong Input Type 5,9 + Hallucinated Object 9,6 + Wrong Attribute 8,6 = **environ 30 %**. TS strict, Go, Kotlin, Rust, OCaml/F#/Gleam et PHPStan niveau 10 couvrent tous cette tranche.
  - _Attrapé en partie selon la force du système_ : Missing Corner Case 15,3 et Incomplete Generation 9,6, soit **environ 25 %**. Null-safety, `match`/`when` exhaustif et erreurs comme valeurs attrapent le sous-ensemble « cas `None` / variante oubliée / erreur ignorée / branche manquante ». Ils n'attrapent pas les off-by-one ni les bornes métier. **C'est la seule tranche où Rust, Kotlin, OCaml/F#/Gleam et, un cran en dessous, TS strict + lint se distinguent de Go**, qui n'a ni types somme ni null-safety, et de PHP, dont l'exhaustivité se vérifie à l'analyse statique et à l'exécution mais sans ADT avec données.
  - _Non attrapable par un système de types_ : Misinterpretation 20,8 + Silly Mistake 9,6 (en grande partie) + Non-Prompted 8,2 + Prompt-biased 6,5 = **environ 45 %**. Seuls les tests, les spécifications et la revue y répondent.
- Le chiffre de 94 % (Mündler) porte sur les **erreurs de compilation**, pas sur les **bugs livrés**. Dans une boucle agentique, ces erreurs sont corrigées par l'agent avant le commit. Le bénéfice du typage tient donc moins au fait que « le bug n'arrive pas en prod » qu'au fait que l'erreur est détectée localement en quelques secondes, avec une localisation précise, sans dépendre d'un test qui l'aurait couverte.
- Le résultat de Bogner et Merkel rappelle que le typage seul n'explique pas la qualité observée. Le facteur dominant reste la discipline de test et de conception, qui chez Cordeau reprend l'architecture hexagonale, Deptrac et la règle « pas de feature sans test domaine ».
- **Spécifique à Rust** (par rapport à « n'importe quel typage fort ») : l'absence de data race garantie à la compilation et le modèle d'ownership (types affines, typestate). Pour un SaaS CRUD + domaine adossé à Postgres, où les handlers sont sans état partagé en mémoire, ces garanties visent une classe de bugs rare. Les vraies courses de Cordeau se jouent au niveau base de données et synchronisation offline (transactions, éditions concurrentes, conflits de sync), et **aucun** des candidats ne les prévient à la compilation.

### Gaps

- Aucune étude trouvée qui mesure, **pour un même jeu de tâches**, le taux de bugs _livrés_ par un agent LLM moderne (2026) selon le langage cible. Les études existantes portent sur le JS humain (Gao), sur des dépôts GitHub (Bogner) ou sur du code LLM en Python et TypeScript avec des modèles de 2023-2024.
- Pas de taxonomie récente des bugs LLM spécifiquement en Rust, Kotlin ou Go qui permettrait de vérifier la projection ci-dessus.

## Q2 — Quelle est la compétence des LLM par langage (benchmarks récents) ?

### Takeaway

Sur les benchmarks **de résolution d'issues réelles**, Rust et Java/Kotlin font _mieux_ que TypeScript/JavaScript et que Go (données 2025, Claude 3.7 Sonnet). PHP s'y place honorablement. Sur les benchmarks de génération de fonctions (AutoCodeBench), Elixir, C# et Rust dominent, et Go ferme la marche. Sur un mini-projet greenfield (Endoh, Opus 4.6, mars 2026), tous les langages atteignent environ 100 % de réussite, mais les langages typés coûtent 1,4 à 2,6 fois plus de temps et de tokens. Aucun benchmark ne donne de ventilation par langage pour les modèles frontière de 2026, et les échantillons sont petits : la « supériorité » de Rust est un signal, pas une preuve.

### Cited Findings

- **SWE-bench Multilingual** : 300 tâches, 42 dépôts, environ 43 tâches par langage. Résolution avec SWE-agent + Claude 3.7 Sonnet : **Rust 58,14 %**, Java 53,49 %, **PHP 48,84 %**, Ruby 43,18 %, **JS/TS 34,88 %**, **Go 30,95 %**, C/C++ 28,57 % (42,67 % au global, contre 63 % sur SWE-bench Verified en Python). — [swebench.com/multilingual](https://www.swebench.com/multilingual.html)
- **Multi-SWE-bench** (ByteDance, avril 2025 ; 1 632 instances ; 7 langages). Meilleur score par langage pour Claude 3.7 Sonnet, toutes méthodes confondues : **Java 23,44 %**, **Rust 15,90 %** (MopenHands), C++ 14,73 %, **TypeScript 11,16 %**, C 8,59 %, **Go 7,48 %**, **JavaScript 5,06 %**. Instances : Java 128, TS 224, JS 356, Go 428, Rust 239, C 128, C++ 129. Les auteurs attribuent la faiblesse de TS/JS aux paradigmes « event-driven, asynchronous », et la force de Rust/Java à une « lower language entropy » ainsi qu'à un code bien documenté et standardisé. — [Multi-SWE-bench, arXiv 2504.02605](https://arxiv.org/html/2504.02605v1)
- **AutoCodeBench** (Tencent, août 2025 ; 3 920 problèmes, 20 langages, environ 196 par langage ; problèmes « multi-logic » ; exécution en sandbox). Claude Opus 4 en mode raisonnement : **Elixir 80,3**, C# 74,9, **Rust 61,0**, Java 55,9, **Kotlin 55,5**, Ruby 52,5, **TypeScript 50,0**, **PHP 44,5**, Python 40,3, Scala 38,7, **Go 37,2** (moyenne 52,4). — [AutoCodeBench, arXiv 2508.09101](https://arxiv.org/html/2508.09101v1)
- José Valim s'appuie sur AutoCodeBench pour affirmer qu'Elixir est « the best language for AI » (immutabilité, documentation, stabilité, outillage pour agents). — [José Valim sur X](https://x.com/josevalim/status/2019422467446698493) ; [Dashbit blog](https://dashbit.co/blog)
- **Endoh** (committer Ruby ; mars 2026 ; Claude Code + Opus 4.6 ; mini-git implémenté dans 13 langages ; 600 runs). Coût moyen et temps par tâche :

  | Langage        | Coût moyen | Temps | Fiabilité |
  | -------------- | ---------- | ----- | --------- |
  | Ruby           | 0,36 $     | 73 s  | 40/40     |
  | Python         | 0,38 $     | 75 s  | 40/40     |
  | JavaScript     | 0,39 $     | 81 s  | 40/40     |
  | **Go**         | **0,50 $** | 102 s | 40/40     |
  | **Java**       | 0,50 $     | 115 s | 40/40     |
  | **Rust**       | **0,54 $** | 114 s | **38/40** |
  | OCaml          | 0,58 $     | 128 s | 40/40     |
  | **TypeScript** | **0,62 $** | 133 s | 40/40     |
  | Haskell        | 0,74 $     | 174 s | 39/40     |

  Python + mypy est 1,6 à 1,7 fois plus lent que Python, et Ruby + Steep 2,0 à 3,2 fois plus lent que Ruby. L'auteur prévient : « The task is too small. Static typing should shine at larger scales », et les dépendances externes sont exclues. — [Endoh, DEV](https://dev.to/mame/which-programming-language-is-best-for-claude-code-508a) ; [InfoQ](https://infoq.com/news/2026/04/ai-coding-language-benchmark)

- **Aider polyglot** : 225 exercices Exercism en C++, Go, Java, JavaScript, Python et Rust. Le leaderboard publie un score agrégé, sans ventilation officielle par langage. — [Aider, polyglot benchmark](https://aider.chat/2024/12/21/polyglot.html)
- Scores agrégés de SWE-bench Multilingual pour les modèles 2026 : environ 84 à 87 % pour les meilleurs modèles Anthropic, environ 82,6 % pour GPT-5.5, **sans ventilation par langage**. Source secondaire, qui confond par endroits Multilingual (300 tâches) et Multi-SWE-bench (1 632). — [CodingFleet, juin 2026](https://codingfleet.com/blog/best-ai-models-rust-coding-2026/)
- **Volume de données d'entraînement (proxy)** : TypeScript est le langage n°1 sur GitHub en nombre de contributeurs depuis août 2025. — [Octoverse 2025](https://github.blog/news-insights/octoverse/octoverse-a-new-developer-joins-github-every-second-as-ai-leads-typescript-to-1/)

### Inferences

- **Incertitude statistique** : avec environ 43 tâches par langage (SWE-bench Multilingual), l'intervalle de confiance à 95 % autour d'un taux de 50 % est d'environ ±15 points. L'écart Rust 58 % / PHP 49 % n'est donc pas significatif. Les écarts Rust 58 % / Go 31 % et Rust 58 % / JS-TS 35 % le sont davantage, mais confondus avec la difficulté propre des dépôts choisis.
- **AutoCodeBench** : les problèmes sont générés _par langage_ sans normalisation de difficulté. Python, le langage le plus représenté dans l'entraînement, y obtient 40 %, moins que Rust, ce qui suggère des jeux de problèmes de difficulté inégale. Il faut lire ce benchmark comme un indicateur de « le modèle sait écrire du X idiomatique », pas comme un classement absolu.
- **Points convergents entre benchmarks** : (a) Rust n'est **pas** un langage où les LLM sont faibles, contrairement à l'intuition « moins de données d'entraînement » ; (b) Go fait systématiquement moins bien que Rust sur ces tâches ; (c) TS/JS sont pénalisés sur la résolution d'issues réelles, probablement par l'hétérogénéité de l'écosystème plus que par le langage ; (d) PHP est correct.
- **Dimension non mesurée** : la _connaissance de l'écosystème_ (versions de frameworks, API de bibliothèques métier). Elle compte beaucoup pour un SaaS métier et favorise les écosystèmes volumineux et stables.
- Le surcoût de 1,4 à 2,6 fois mesuré par Endoh est un **coût d'itération de l'agent**, pas un coût de maintenance. Sur un projet de la taille de Cordeau, où le refactoring est fréquent et les invariants métier nombreux, il est plausible que la courbe s'inverse ; l'auteur l'admet lui-même. Ce n'est toutefois pas démontré.

### Gaps

- Aucune ventilation par langage publiée pour les modèles frontière de 2026 (Opus 4.x/5, GPT-5.x) sur SWE-bench Multilingual ou Multi-SWE-bench.
- Aider polyglot ne publie pas de score par langage sur son leaderboard.
- Pas de benchmark incluant Gleam, F# ou Kotlin backend en résolution d'issues.
- Pas de chiffre fiable sur le volume de tokens d'entraînement par langage (The Stack v2 ou équivalent non consulté).

## Q3 — Quelle est la vitesse de la boucle de feedback (type-check, compilation, tests) ?

### Takeaway

Go reste la référence en vitesse de compilation et en cache de tests. TypeScript a fait un saut majeur avec TS 7 natif (GA le 8 juillet 2026, 8 à 12 fois plus rapide sur de gros projets, environ 3 fois mesuré sur un monorepo réel). Rust reste le plus lent en rebuild incrémental (55 % des répondants à l'enquête officielle attendent plus de 10 s), ce que `cargo check` atténue. Mesurée en temps de bout en bout de l'agent, la différence se tasse : Rust 114 s contre TS 133 s contre Go 102 s chez Endoh.

### Cited Findings

- **Rust, enquête « Compiler performance survey 2025 »** (plus de 3 700 réponses) : satisfaction moyenne de 6/10, **55 % attendent plus de 10 s** pour un rebuild incrémental. Les rebuilds après une petite modification sont le principal point de douleur. Chantiers en cours : linker LLD par défaut, cache, `hint-mostly-unused`. — [Rust Blog, 10/09/2025](https://blog.rust-lang.org/2025/09/10/rust-compiler-performance-survey-2025-results)
- `cargo check` (sans génération de code) est 2 à 3 fois plus rapide que `cargo build` et constitue la boucle de feedback recommandée. — [InfoWorld](https://www.infoworld.com/article/4115425/rust-slow-to-compile-heres-how-to-speed-it-up.html) ; [corrode.dev](https://corrode.dev/blog/tips-for-faster-rust-compile-times/)
- **TypeScript 7** (« Project Corsa », compilateur réécrit en Go) : RC le 18 juin 2026, **GA le 8 juillet 2026 (7.0.2)**. Type-check de VS Code : 125,7 s en TS 6, 10,6 s en TS 7 (×11,9). Sur un monorepo Next.js réel, environ ×3 seulement. — [Visual Studio Magazine](https://visualstudiomagazine.com/articles/2026/06/22/typescript-7-0-rc-moves-microsofts-go-rewrite-into-the-mainline-compiler.aspx) ; [digitalapplied, GA](https://www.digitalapplied.com/blog/typescript-7-0-ga-native-compiler-migration-playbook-2026) ; [retour d'expérience monorepo, DEV](https://dev.to/curioustore_48788631d0e2e/i-ran-typescript-7s-native-compiler-tsgo-on-our-monorepo-4d6) ; [dreaming.press](https://dreaming.press/posts/2026-07-11-typescript-7-go-native-compiler-ships.html)
- **Go selon Ronacher** : « In Go, tests run straightforwardly and incrementally, significantly enhancing the agentic workflow ». Il cite le cache de tests comme décisif pour les boucles agentiques. — [Ronacher, Agentic Coding Recommendations (juin 2025)](https://lucumr.pocoo.org/2025/6/12/agentic-coding/)
- **Python selon Ronacher** : « the agent loop is really slow… the interpreter to boot up and initialize the entire application ». — [Ronacher, juin 2025](https://lucumr.pocoo.org/2025/6/12/agentic-coding/)
- **Temps agent de bout en bout** (Endoh, Opus 4.6) : Go 101,6 s ± 37, Java 115,4 s, Rust 113,7 s ± 54,8, TypeScript 133,0 s ± 29,4, OCaml 128,1 s. — [Endoh, DEV](https://dev.to/mame/which-programming-language-is-best-for-claude-code-508a)

### Inferences

- Pour un agent, la latence pertinente est celle du **check incrémental et des tests ciblés**, pas celle du build release. Dans ce régime, on peut estimer le classement suivant : Go ≈ PHP (pas de compilation ; PHPStan avec cache de résultats) ≈ TS 7 > Kotlin ≈ Rust. Les deux derniers se situent à quelques secondes à quelques dizaines de secondes sur un workspace moyen ; c'est une estimation, sans mesure spécifique pour Kotlin.
- Les tests d'intégration Rust (binaire de test par crate, liaison) coûtent davantage que le seul `cargo check`. Un workspace découpé en crates fines (domaine pur sans dépendances lourdes) réduit fortement ce coût, de façon analogue au découpage hexagonal actuel.
- Le chiffre d'Endoh montre que la lenteur du compilateur Rust ne domine pas le temps total sur une petite tâche : c'est le temps de raisonnement du modèle qui domine. Sur une grosse base de code avec beaucoup de dépendances (Axum, SQLx, Tokio, sérialisation), le poids du compilateur augmente.

### Gaps

- Pas de mesure publique comparable de PHPStan niveau 10 ou de Psalm sur une base de code de la taille de Cordeau.
- Pas de mesure publique de Kotlin K2 (Gradle) en rebuild incrémental comparable à l'enquête Rust.
- Pas de mesure de SQLx en mode « offline » dans la boucle agent.

## Q4 — Que disent les praticiens avancés de l'agentic coding sur le meilleur langage pour les agents ?

### Takeaway

Il n'y a **pas de consensus**. Chaque camp met en avant une propriété différente :

- Ronacher (Go) : la simplicité, la greppabilité, le cache de tests et la stabilité de l'écosystème ;
- zackoverflow, Belderbos, HAMY (Rust) : le compilateur strict comme garde-fou ;
- Valim (Elixir) : immutabilité, documentation et stabilité ;
- Endoh (langages dynamiques) : coût et vitesse sur de petites tâches ;
- GitHub Octoverse (TypeScript) : les types comme contrats.

Les propriétés invoquées (explicite, local, erreurs comme valeurs, stabilité, feedback rapide) sont _transverses_. Aucune n'est propre à Rust, sauf la conjonction « types forts et bas niveau ».

### Cited Findings

- **Armin Ronacher, juin 2025 (pro-Go pour les nouveaux backends)** : il cite le contexte explicite, le cache de tests, la simplicité (« Go is sloppy… Substitute 'developers' with 'agents' »), les interfaces structurelles (« very little surprise for the agent ») et la compatibilité arrière (« Go's entire ecosystem embraces backwards compatibility and explicit version moves »). Sur Rust : « agents sometimes fail because they misunderstand `cargo test`'s invocation syntax ». Sur JS : son « fast-moving ecosystem » pousse les agents à générer des patterns obsolètes. — [lucumr.pocoo.org, 2025-06-12](https://lucumr.pocoo.org/2025/6/12/agentic-coding/) ; [Simon Willison, résumé](https://simonwillison.net/2025/Jun/12/agentic-coding-recommendations/)
- **Armin Ronacher, février 2026 (« A Language For Agents »)** : les agents réussissent mieux avec du code explicite, greppable, permettant un raisonnement local, des builds déterministes et des erreurs typées plutôt que des exceptions. Il critique l'**inférence de types lourde** : « you now need an LSP or… compiler error messages to figure out what the type of the expression is. Agents struggle with this too. » Il note que « the agent does much better with TypeScript » que Python. Rust n'est pas cité dans ce billet. — [lucumr.pocoo.org, 2026-02-09](https://lucumr.pocoo.org/2026/2/9/a-language-for-agents/)
- **zackoverflow, mars 2026 (pro-Rust)** : Rust combine un accès bas niveau et un système de types « Standard ML / Haskell / Hindley-Milner style » capable d'« encode important constraints ». Avec les agents, la verbosité qui coûtait « a material drop in productivity » disparaît (« you really get to have your cake and eat it too »). Il observe qu'en TypeScript les agents se rabattent sur des `if/else` au lieu de matchings exhaustifs, ce qui produit des bugs. — [zackoverflow.dev](https://zackoverflow.dev/writing/rust-is-the-best-language-for-coding-agents/)
- **Bob Belderbos, HAMY (pro-Rust)** : le compilateur Rust comme « guardrail » pour le code d'agent, avec cet argument : plus les messages d'erreur sont bons, mieux l'agent itère. — [Belderbos](https://belderbos.dev/blog/rust-compiler-ai-agent-guardrail/) ; [HAMY, avril 2026](https://hamy.xyz/blog/2026-04_rust-age-of-ai)
- **José Valim, février 2026 (pro-Elixir)** : immutabilité (« spooky action at a distance » en POO mutable), documentation, stabilité, outillage pour agents. — [José Valim sur X](https://x.com/josevalim/status/2019422467446698493) ; [CodeMySpec, synthèse](https://codemyspec.com/blog/why-elixir-is-the-best-language-for-llms)
- **Yusuke Endoh, mars 2026 (langages dynamiques sur petit périmètre)** : Ruby, Python et JS sont « the fastest, cheapest, and most stable », mais il reconnaît que le typage statique « should shine at larger scales ». — [DEV](https://dev.to/mame/which-programming-language-is-best-for-claude-code-508a)
- **GitHub (Octoverse 2025, pro-typage, TS en tête)** : « Typed contracts scale AI-assisted teams ». — [GitHub Blog](https://github.blog/news-insights/octoverse/octoverse-a-new-developer-joins-github-every-second-as-ai-leads-typescript-to-1/)
- **Enquête Stack Overflow 2025** : Rust est le langage le plus « admired » (72 %), devant **Gleam (70 %)**, Elixir (66 %) et Zig (64 %). — [Stack Overflow Survey 2025, Technology](https://survey.stackoverflow.co/2025/technology)

### Inferences

- **Tension Ronacher contre Rust** : sa critique de « l'inférence lourde » et de la magie vise implicitement les codes Rust riches en traits génériques, en lifetimes et en macros, et aussi les types TS « gymnastiques ». Un Rust « agent-friendly » serait donc un Rust **volontairement simple** : types concrets, newtypes, enums, `Result`, peu de génériques. C'est une discipline à écrire dans le `CLAUDE.md`, pas une propriété du langage.
- **Points d'accord entre camps** : erreurs comme valeurs, stabilité de l'écosystème, raisonnement local, boucle de feedback rapide. Rust coche les trois premiers. Go coche stabilité et vitesse mais pas les erreurs non ignorables. TS coche la vitesse (TS 7) mais pas la stabilité de l'écosystème. Kotlin et OCaml/F#/Gleam cochent l'essentiel, avec un écosystème plus petit (Gleam, OCaml) ou plus lourd (JVM).
- Les avis pro-Rust viennent surtout de contextes **systèmes ou graphiques**, peu de SaaS métier CRUD. Les avis pro-Go (Ronacher) viennent de contextes backend web. Aucun praticien trouvé ne documente un SaaS métier B2B complet construit en Rust par un agent.

### Gaps

- Pas trouvé de retour d'expérience long (plus de 6 mois) d'un solo founder qui maintient un SaaS métier en Rust essentiellement via des agents.
- Les commentaires critiques (Hacker News) sur la méthodologie d'AutoCodeBench et l'argument Elixir n'ont pas été lus en détail.

## Q5 — Partage de code avec les clients TS (React web, Expo offline-first) : comment chaque option s'y prend, et quel poids donner à ce critère ?

### Takeaway

Pour une app offline-first qui doit calculer **les mêmes règles métier** sur l'appareil et sur le serveur (calculs de mesures, totaux, validations, statuts), TypeScript de bout en bout offre un partage **gratuit et direct**. Rust et Kotlin offrent une source unique mais via FFI ou WASM et des modules natifs, ce qui ajoute un toolchain natif à la chaîne Expo. Gleam, F# (Fable) et OCaml (Melange) compilent vers JS, ce qui est une voie intermédiaire. PHP et Go n'offrent aucun partage réaliste. C'est le critère où l'écart entre candidats est le plus **binaire**.

### Cited Findings

- **Rust vers React Native / Expo** : `uniffi-bindgen-react-native` génère des bindings TypeScript (Turbo Modules via JSI C++, WASM pour le web, N-API pour Node) à partir de code Rust UniFFI, pour « write your business logic once in Rust and access it seamlessly from TypeScript ». Usage en prod cité : ChessTiles sur iOS. — [jhugman/uniffi-bindgen-react-native](https://github.com/jhugman/uniffi-bindgen-react-native) ; [guide](https://jhugman.github.io/uniffi-bindgen-react-native/) ; [Mozilla UniFFI](https://github.com/mozilla/uniffi-rs)
- Une recette d'intégration Rust + UniFFI + Expo existe. — [claas.dev, Expo with Rust](https://claas.dev/posts/expo-with-rust/)
- **Kotlin Multiplatform** : stable depuis novembre 2023, soutenu officiellement par Google pour partager la logique métier Android/iOS. Compose Multiplatform iOS est stable depuis mai 2025. Selon l'enquête JetBrains citée, l'adoption de KMP chez les développeurs Kotlin est passée de 7 % à 18 % en un an. Exemples cités : Cash App, Netflix, Duolingo. — [Android Developers, KMP](https://developer.android.com/kotlin/multiplatform) ; [Volpis](https://volpis.com/blog/is-kotlin-multiplatform-production-ready/) ; [JetBrains, KMP stable](https://blog.jetbrains.com/kotlin/2023/11/kotlin-multiplatform-stable/)
- JetBrains publie une comparaison KMP / React Native, ce qui en fait deux stratégies distinctes plutôt que combinables par défaut. — [kotlinlang.org, KMP vs React Native](https://kotlinlang.org/docs/multiplatform/kotlin-multiplatform-react-native.html)
- **Langages fonctionnels compilant vers JS** : Gleam compile vers Erlang et **JavaScript** — [gleam.run](https://gleam.run/) ; F# via Fable — [fable.io](https://fable.io/) ; OCaml via Melange — [melange.re](https://melange.re/).
- **Effect** (cf. Q6) fonctionne côté serveur comme côté client, avec un cœur sans dépendance et un bundle de 7,1 kB min+gzip en v4. — [Effect 4.0](https://effect.website/blog/releases/effect/40)

### Inferences

- **Coût concret pour Cordeau d'un domaine en Rust partagé** :
  - un toolchain Rust cross-compilé pour iOS et Android dans le build EAS ;
  - un dev client au lieu d'Expo Go, déjà le cas avec les modules natifs ;
  - des bindings régénérés à chaque changement d'API du domaine ;
  - un build WASM pour le web ;
  - le débogage qui traverse la frontière JSI.

  C'est faisable mais lourd, et chaque étape est un endroit où un agent peut se perdre (scripts de build natif, Xcode). Le job CI de build natif iOS (#87) illustre déjà ce coût.

- **Alternative pragmatique** : ne partager que les **contrats** (types générés via OpenAPI, ce que fait déjà `packages/shared`) et dupliquer la logique métier en TS côté mobile, avec des **tests de conformité partagés** (fixtures JSON entrée/sortie exécutées des deux côtés). Ce schéma fonctionne avec n'importe quel backend (Rust, Go, Kotlin, PHP). Il remplace le partage de code par un partage de _spécifications exécutables_. C'est une déduction et non un pattern sourcé, mais il est indépendant du langage.
- Le poids de ce critère dépend du **volume de logique métier dupliquée**. Si l'essentiel des règles (calcul des lots et tâches, mesures, totaux de devis, TVA) doit tourner offline sur l'appareil, il devient l'un des plus lourds de la matrice et favorise fortement TS de bout en bout. S'il se limite à des validations simples, des tests de conformité suffisent.
- KMP est surtout pertinent avec une UI native ou Compose. Avec Expo/React Native, il redevient un module natif comme Rust, sans avantage net sur Rust de ce point de vue.

### Gaps

- Pas trouvé de retour d'expérience publié d'une app **Expo offline-first** partageant un domaine Rust via UniFFI en production, au-delà d'exemples isolés comme ChessTiles.
- Pas d'information vérifiée sur l'intégration KMP dans Expo (modules Expo en Kotlin/Swift possibles, mais sans recette KMP officielle trouvée).

## Q6 — Erreurs typées en TypeScript (Effect-TS, fp-ts) : maturité, adoption et compétence des LLM

### Takeaway

Effect 4.0 est sorti le **30 septembre 2026** (la veille de ces notes) : réécriture complète, LTS d'au moins 3 ans, bundle 5 fois plus petit. L'adoption brute est massive en téléchargements, mais la v4 n'a pratiquement **aucune présence** dans les données d'entraînement des modèles actuels. Le risque que l'agent génère de l'Effect v3 obsolète est donc élevé à court terme. fp-ts a été absorbé par Effect.

### Cited Findings

- **Effect 4.0** est publié le 30 septembre 2026 et décrit comme « rebuilt from the ground up ». Côté performances : bundle 35,6 kB → 7,1 kB (min+gzip), débit de tâches concurrentes ×6,4, mémoire par fiber réduite de 86 %. — [Effect blog, 4.0](https://effect.website/blog/releases/effect/40)
- **Engagement LTS** : corrections de bugs au moins jusqu'en septembre 2029 (ou un an après la 5.0), correctifs de sécurité au moins jusqu'en septembre 2029 (ou deux ans après la 5.0). — [Effect blog, 4.0](https://effect.website/blog/releases/effect/40)
- **Adoption** : 43,9 M de téléchargements npm hebdomadaires (semaine du 21/09/2026), dont 56 % pour la 4.x contre 44 % pour la 3.x dès la première semaine. — [Effect blog, 4.0](https://effect.website/blog/releases/effect/40). Environ 3 448 paquets npm dépendent d'`effect`. — [npm, effect](https://www.npmjs.com/package/effect)
- **Outillage pour agents** : l'équipe propose un « LLM Guide » et suggère de confier la migration v3 → v4 à « your coding agent » (« it should do most of the work on its own »). — [Effect blog, 4.0](https://effect.website/blog/releases/effect/40)
- **Effect v4 bêta** (avril 2026) : runtime réécrit, système de paquets unifié. — [InfoQ, Effect v4 Beta](https://www.infoq.com/news/2026/04/effect-v4-beta/)
- **Constat de praticien** : en TypeScript, les agents se rabattent sur des `if/else` au lieu de matchings exhaustifs. — [zackoverflow](https://zackoverflow.dev/writing/rust-is-the-best-language-for-coding-agents/)

### Inferences

- Les 43,9 M de téléchargements hebdomadaires incluent sans doute beaucoup de dépendances **transitives** (outils qui embarquent Effect). Ils mesurent donc la diffusion plus que la base d'utilisateurs directs. C'est une déduction ; la ventilation n'a pas été trouvée.
- Une **réécriture majeure publiée la veille** est exactement le cas de « churn » que Ronacher identifie comme toxique pour les agents. Adopter Effect aujourd'hui, c'est accepter quelques mois où l'agent produit de l'API v3 à corriger, atténués par le « LLM Guide » et des skills et docs injectés dans le contexte.
- Effect apporte en TS ce que Rust donne nativement : erreurs dans le type de retour, injection de dépendances typée, concurrence structurée. Il le fait au prix d'un **style de code très différent** de TS idiomatique, d'une courbe d'apprentissage et d'une dépendance forte à une seule bibliothèque. Des alternatives plus légères (unions discriminées `Result` maison, `neverthrow`) couvrent l'essentiel des « erreurs comme valeurs » sans adopter le runtime Effect.
- Pour Cordeau, un domaine TS en fonctions pures, avec unions discriminées, un `Result` maison et la règle de lint d'exhaustivité, capte une bonne part du bénéfice « Rust-like » sans la dépendance Effect. Effect se justifie surtout pour l'orchestration d'effets (sync offline, retries, files d'attente).

### Gaps

- Aucun benchmark de compétence des LLM sur Effect, en v3 comme en v4.
- Pas de chiffre d'adoption « directe » (projets applicatifs) d'Effect distinct des dépendances transitives.
- Pas de données vérifiées sur l'état de maintenance de fp-ts en 2026.

## Q7 — Adéquation de l'écosystème à un SaaS métier français (Postgres, auth, PDF, facturation électronique, paiement), coût opérationnel et stabilité à long terme

### Takeaway

Pour les briques « administratives » d'un SaaS français, l'écosystème le plus mûr est la **JVM** (Mustang pour Factur-X, SDK Stripe officiel, Spring Security). Viennent ensuite **PHP/Symfony** (déjà en place) et **TypeScript**, puis Go. **Rust est le plus maigre** : Stripe y est communautaire, Factur-X « émergent », l'auth est à assembler soi-même. En contrepartie, Rust et Go gagnent sur la simplicité et le coût d'exploitation (binaire statique), ainsi que sur la stabilité du langage. La réforme de la facturation électronique (émission obligatoire pour les TPE et micro-entreprises au 1er septembre 2027) rend la brique Factur-X/PA structurante pour Cordeau.

### Cited Findings

**Facturation électronique**

- **Calendrier** :
  - au 1er septembre 2026, toutes les entreprises assujetties à la TVA doivent pouvoir **recevoir** des factures électroniques, et les grandes entreprises et ETI doivent en **émettre** ;
  - au **1er septembre 2027**, les PME, TPE et micro-entrepreneurs doivent émettre et faire l'e-reporting.

  — [Cegid, calendrier](https://www.cegid.com/fr/facture-electronique-obligatoire/calendrier-facture-electronique/) ; [mafacturation-electronique.fr](https://mafacturation-electronique.fr/calendrier-facturation-electronique)

- **Plateformes agréées (PA)** : elles doivent toutes prendre en charge Factur-X, UBL et CII. La version actuelle de Factur-X est la 1.08 (alignée sur ZUGFeRD 2.4), applicable depuis le 15 janvier 2026. — [ma-facture-electronique.org](https://ma-facture-electronique.org/formats-normes/factur-x/)
- **Bibliothèques Factur-X open source** (article du 31 mars 2026) :

  | Langage      | Bibliothèque                                     | Profils          | PDF/A-3        | Validation                       |
  | ------------ | ------------------------------------------------ | ---------------- | -------------- | -------------------------------- |
  | Python       | factur-x (Akretion), implémentation de référence | tous             | automatique    | —                                |
  | Java         | **Mustang**, la plus complète                    | tous             | oui            | intégrée (+ CLI et serveur REST) |
  | .NET         | ZUGFeRD-csharp                                   | jusqu'à EN 16931 | —              | —                                |

- Il existe aussi un SDK **TypeScript** pur pour Factur-X au profil EN 16931 (génération, embarquement, extraction). — [Geekles007/facturx](https://github.com/Geekles007/facturx)

**Paiement, framework web, auth**

- **Stripe** : SDK serveur officiels pour Ruby, Python, PHP, Java, Node, Go et .NET — [Stripe docs, SDKs](https://docs.stripe.com/sdks). Pour Rust, `async-stripe` est **communautaire**, généré depuis la spec OpenAPI officielle et mis à jour chaque semaine par CI. — [arlyon/async-stripe](https://github.com/arlyon/async-stripe) ; [crates.io](https://crates.io/crates/async-stripe)
- **Rust web** : Axum est le framework le plus téléchargé sur crates.io. L'authentification se fait typiquement par extracteurs personnalisés, et Loco (framework « à la Rails ») est décrit comme « still young and evolving ». — [Leapcell, Axum](https://leapcell.medium.com/axum-is-shaping-the-future-of-web-development-in-rust-07e860ff9b87) ; [StarterPick, 2026](https://starterpick.com/guides/best-rust-web-starters-2026)

**Stabilité à long terme**

- **Go** : promesse de compatibilité Go 1. — [go.dev/doc/go1compat](https://go.dev/doc/go1compat)
- **Rust** : système d'éditions pour faire évoluer le langage sans casser l'existant. — [Rust Edition Guide](https://doc.rust-lang.org/edition-guide/)
- **JS/TS** : Ronacher pointe le « fast-moving ecosystem ». — [Ronacher 2025](https://lucumr.pocoo.org/2025/6/12/agentic-coding/). Exemples récents de ruptures : TS 6 → 7 (réécriture du compilateur), Effect 3 → 4 (réécriture). — [Visual Studio Magazine](https://visualstudiomagazine.com/articles/2026/06/22/typescript-7-0-rc-moves-microsofts-go-rewrite-into-the-mainline-compiler.aspx) ; [Effect 4.0](https://effect.website/blog/releases/effect/40)
- **SQL vérifié à la compilation, disponible dans plusieurs écosystèmes** : SQLx (Rust) — [sqlx](https://github.com/launchbadge/sqlx) ; sqlc (Go) — [sqlc.dev](https://sqlc.dev/) ; jOOQ et SQLDelight (Kotlin/JVM) — [jOOQ](https://www.jooq.org/) ; Kysely (TS) — [kysely.dev](https://kysely.dev/).

### Inferences

- **La facturation électronique n'impose pas forcément une bibliothèque Factur-X locale.** Pour un SaaS d'artisans, l'option réaliste est souvent de s'intégrer à une PA par API HTTP/JSON (la PA produit et valide Factur-X, UBL et CII), ce qui rend la brique **agnostique du langage**. Si Cordeau doit générer lui-même du Factur-X/PDF-A-3 validé, les écosystèmes Java (Mustang) et Python (Akretion) sont nettement devant. Rust et Go supposeraient soit un microservice JVM ou Python, soit d'écrire et valider soi-même le XML CII et le PDF/A-3. C'est un chantier à risque réglementaire.
- **Auth et données personnelles (RGPD)** : sessions, refresh tokens, reset de mot de passe, rate limiting, éventuellement OAuth. Symfony Security et Spring Security offrent des briques intégrées et éprouvées. En Rust, il faut assembler des crates (sessions, argon2, JWT, CSRF), et un agent peut alors introduire des failles subtiles qu'aucun compilateur ne voit. C'est un **contre-argument fort au « solide »** pour Rust dans ce périmètre précis.
- **Coût d'exploitation** (pas de chiffres sourcés, ordre de grandeur) : un binaire statique Rust ou Go démarre vite et consomme peu de mémoire, la JVM davantage, Node et PHP sont entre les deux. À l'échelle de Cordeau (bêta avec quelques dizaines à centaines d'artisans), l'écart d'hébergement se compte en euros par mois. Il pèse peu face au temps de développement.
- **Postgres** : tous les candidats disposent de pilotes mûrs. La différenciation porte sur le **SQL vérifié à la compilation** (SQLx, sqlc, jOOQ, Kysely), qui n'est **pas propre à Rust**. Doctrine (PHP) n'offre pas d'équivalent aussi strict sur le SQL brut.
- Le SDK Stripe Rust généré depuis l'OpenAPI officielle réduit le risque, mais reste hors du support officiel. C'est un risque de maintenance à long terme (mainteneur unique ou petite équipe).

### Gaps

- Pas d'état des lieux vérifié des bibliothèques PDF par langage (génération de devis et factures avec mise en page riche) : typst et printpdf en Rust, pdf-lib et Puppeteer en TS, dompdf et TCPDF en PHP, iText et PDFBox en JVM.
- `horstoeko/zugferd` (PHP), souvent cité comme plus complet que factur-x-php, n'apparaît pas dans la source consultée et son niveau de profil n'a pas été vérifié.
- Pas de liste vérifiée des PA proposant une API REST adaptée aux éditeurs de SaaS, ni de leur SDK par langage.
- Pas de chiffres sourcés de coût d'hébergement comparé (mémoire et CPU) pour une API métier équivalente dans chaque langage.

## Q8 — Statu quo PHP 8.5 durci (PHPStan max + strict-rules + bleeding edge, Psalm, Infection, Deptrac) : à quelle distance se situe-t-il ?

### Takeaway

PHPStan niveau 10 avec strict-rules et bleeding edge, plus Deptrac et Infection, couvre **la quasi-totalité de la tranche « typage de base »** (environ 30 % des bugs LLM, cf. Q1) et une partie de la tranche « forte » : null-safety statique, exhaustivité sur les enums et génériques via PHPDoc. Il manque trois choses : de vrais **ADT avec données** (les enums PHP n'ont pas de payload), des **erreurs comme valeurs** idiomatiques, et la **solidité de bout en bout**, puisque le typage repose sur un analyseur externe au-dessus d'un runtime dynamique, où les annotations peuvent mentir. Les LLM sont compétents en PHP : 48,8 % sur SWE-bench Multilingual, devant JS/TS et Go.

### Cited Findings

- **PHPStan 2.x** : niveaux 0 à 10. Le niveau 10 (`max`) vérifie notamment l'usage de `mixed` et la validité des appels sur toutes les branches d'un type union. — [PHPStan Rule Levels](https://phpstan.org/user-guide/rule-levels) ; [Upgrading to PHPStan 2.0](https://phpstan.org/blog/upgrading-from-phpstan-1-to-2)
- **phpstan-strict-rules** : règles supplémentaires « strictly and strongly typed code with no loose casting ». **Bleeding edge** : active dès maintenant les règles de la prochaine version majeure. — [PHPStan 1.12, Road to 2.0](https://phpstan.org/blog/phpstan-1-12-road-to-phpstan-2-0) ; [PocketArC, Hardcore PHPStan](https://pocketarc.com/phpstan)
- **Génériques** : en PHP, ils sont exprimés par annotations PHPDoc (`@template`), vérifiées par l'analyseur statique et non par le moteur. — [PHPStan, Generics in PHP using PHPDocs](https://phpstan.org/blog/generics-in-php-using-phpdocs)
- **Exceptions** : PHPStan peut vérifier les exceptions déclarées (`@throws`), ce qui revient à des « checked exceptions » optionnelles. — [PHPStan, Bring your exceptions under control](https://phpstan.org/blog/bring-your-exceptions-under-control)
- **Enums PHP (8.1)** : purs ou « backed » (int/string), sans données associées par cas. — [PHP manual, Enumerations](https://www.php.net/manual/en/language.enumerations.php). **Classes readonly** depuis PHP 8.2. — [PHP 8.2 release](https://www.php.net/releases/8.2/en.php)
- **Infection** (mutation testing) mesure l'efficacité réelle des tests : il injecte des mutants et vérifie que les tests échouent. — [Infection](https://infection.github.io/)
- **Deptrac** fait respecter les dépendances entre couches et contextes, déjà en place chez Cordeau. — [deptrac/deptrac](https://github.com/deptrac/deptrac)
- **Compétence des LLM en PHP** : 48,84 % sur SWE-bench Multilingual (Claude 3.7 Sonnet), devant JS/TS (34,88 %) et Go (30,95 %) — [swebench.com/multilingual](https://www.swebench.com/multilingual.html) ; 44,5 % sur AutoCodeBench (Opus 4), devant Go (37,2 %) — [AutoCodeBench](https://arxiv.org/html/2508.09101v1).
- **Tendance d'usage** : PHP continue de perdre du terrain dans l'enquête Stack Overflow 2025, alors que TS progresse. — [Stack Overflow Survey 2025](https://survey.stackoverflow.co/2025/technology) ; [synthèse](https://www.frameworktraining.co.uk/news-insights/stackoverflow-developer-survey-results-2025-overview)

### Inferences

- **Écart avec Rust, garantie par garantie** :

  | Garantie                     | PHP durci                                                                           | Rust                    |
  | ---------------------------- | ----------------------------------------------------------------------------------- | ----------------------- |
  | Null-safety                  | ≈ équivalente en pratique (PHPStan 10)                                              | native                  |
  | Matching exhaustif           | sur les enums, via PHPStan et `match`                                               | sur tous les ADT, natif |
  | ADT avec données             | approximation par hiérarchies `final` + interfaces `sealed` en PHPDoc, plus verbeux | natif                   |
  | Immutabilité                 | `readonly` opt-in                                                                   | par défaut              |
  | Erreurs comme valeurs        | possibles mais non idiomatiques                                                     | natives                 |
  | Data races                   | non pertinent (un processus par requête)                                            | natif                   |
  | SQL vérifié à la compilation | absent avec Doctrine                                                                | SQLx                    |

- **Le maillon faible de PHP durci, c'est l'échappatoire.** `@phpstan-ignore`, baselines et `@var` mensongers permettent à un agent de « faire passer » l'analyse. Une règle CI qui interdit toute nouvelle entrée de baseline ou d'ignore, avec revue, ferme une grande partie de cette fente. Rust a son équivalent (`unwrap()`, `unsafe`, `#[allow]`), qui se contrôle aussi par lint (clippy `unwrap_used`, `forbid(unsafe_code)`).
- **Infection est un levier sous-estimé**, quel que soit le langage. Il attaque la tranche « bugs fonctionnels » (environ 45 %, cf. Q1), qu'aucun typage n'atteint, en vérifiant que les tests écrits par l'agent détectent réellement les régressions. Des équivalents existent en Rust (cargo-mutants), en TS (Stryker) et sur la JVM (PIT). C'est l'outil le plus directement lié au « solide » recherché, et il n'impose aucune migration.
- **Estimation** : le statu quo durci capte peut-être 70 à 80 % du bénéfice « compile-time » qu'apporterait Rust sur ce domaine métier. Il garde un écosystème mûr (Symfony, API Platform, Stripe officiel, auth intégrée) et ne coûte aucune migration. Le reste de l'écart tient surtout aux ADT avec données et aux erreurs comme valeurs, qu'une discipline de conception (value objects, `Result` maison, enums + `match`) peut en partie émuler.

### Gaps

- Pas trouvé d'étude quantifiant la réduction de bugs apportée par PHPStan niveau max par rapport à un niveau inférieur, ni par Psalm.
- Le comportement exact de PHPStan 2.x sur l'exhaustivité de `match` pour les unions de classes (et pas seulement les enums) n'a pas été vérifié dans la documentation.
- Les apports de PHP 8.5 (pipe operator, etc.) au typage n'ont pas été vérifiés dans les sources.

## Q9 — Synthèse : matrice comparative, classement par critère, et ce qui est propre à Rust

### Takeaway

**Ce qui est propre à Rust** :

- l'absence de data races garantie à la compilation et l'ownership (bénéfice faible pour un SaaS CRUD + domaine sans état partagé) ;
- la culture « erreurs comme valeurs » imposée par la stdlib (`Result` `#[must_use]`, `?`) ;
- la conjonction bas niveau + système de types expressif ;
- un très bon score sur les benchmarks de résolution d'issues de 2025 (non significatif statistiquement pour certains écarts).

**Ce qui vient de n'importe quel typage statique fort** : null-safety, types somme et matching exhaustif, value objects et newtypes, SQL vérifié à la compilation. Kotlin, OCaml/F#/Gleam et, dans une large mesure, TS strict et PHPStan 10 les partagent.

**Ce que Rust coûte spécifiquement pour Cordeau** :

- compilation incrémentale la plus lente ;
- écosystème SaaS français le plus maigre (Stripe communautaire, Factur-X émergent, auth à assembler) ;
- partage avec Expo uniquement via FFI ou WASM ;
- complexité de traits et d'inférence que Ronacher juge défavorable aux agents.

#### Classement par critère, avec un raisonnement court

1. **Garanties à la compilation** : Rust > OCaml/F#/Gleam ≈ Kotlin > TS strict (+Effect, +lint d'exhaustivité) > PHP 8.5 durci > Go ≈ Elixir.
   - _Pourquoi_ : Rust est seul à cumuler ADT, absence de `null`, `Result` must_use, immutabilité par défaut et absence de data race. Ses suivants n'ont pas la garantie sur les data races, peu utile ici. TS perd des points sur la non-sûreté et sur des erreurs non typées par défaut. Go perd sur l'absence de types somme et sur `nil`.
2. **Vitesse de la boucle de feedback** : Go > TS 7 ≈ PHP > Gleam/OCaml (non mesuré) > Kotlin ≈ Rust.
   - _Pourquoi_ : le cache de tests de Go et TS natif d'un côté ; le rebuild incrémental Rust de l'autre. En temps agent total sur une petite tâche, Rust ≈ Java < TS.
3. **Compétence des LLM** :
   - en résolution d'issues : Rust ≈ Java/Kotlin > PHP > TS/JS > Go ;
   - en connaissance d'écosystème et de bibliothèques métier : TS > PHP ≈ Java/Kotlin > Go > Rust > Gleam/F#/OCaml.
   - _Pourquoi_ : les benchmarks 2025 favorisent Rust, mais avec de petits échantillons ; le volume de code et de bibliothèques favorise TS.
4. **Écosystème SaaS français** : Kotlin/JVM > PHP/Symfony > TS > Go > Rust > OCaml/Gleam. F# hérite de .NET.
   - _Pourquoi_ : Factur-X (Mustang), SDK Stripe officiels, auth intégrée. Cet écart se réduit si la facturation passe par l'API d'une PA.
5. **Partage avec les clients TS** : TS >> Gleam/F#/OCaml (→ JS) > Rust ≈ Kotlin (FFI / module natif) > Go ≈ PHP ≈ Elixir.
   - _Pourquoi_ : seul TS partage le même code sans frontière ni toolchain natif.
6. **Coût et simplicité d'exploitation** : Rust ≈ Go > TS ≈ PHP (existant) ≈ Elixir > Kotlin/JVM.
   - _Pourquoi_ : binaire statique et mémoire. À l'échelle de Cordeau, l'impact financier est faible.
7. **Maintenabilité à long terme** : Go > Rust ≈ Kotlin ≈ Elixir > PHP/Symfony > Gleam/OCaml/F# > TS.
   - _Pourquoi_ : stabilité du langage et churn des bibliothèques, que Ronacher juge décisif pour les agents.

#### Ce que cela isole sur la question « tout passer en Rust »

- **La robustesse agent-friendly vient surtout de trois ingrédients non spécifiques** :
  1. un typage fort avec null-safety, types somme et exhaustivité, et des erreurs comme valeurs ;
  2. une boucle de feedback rapide et déterministe (check incrémental et tests ciblés en cache) ;
  3. un écosystème stable, avec des tests efficaces vérifiés par mutation testing.

  Rust excelle sur le premier, est moyen sur le deuxième et moyen sur le troisième côté bibliothèques métier.

- **Ce que Rust apporte en propre** (data races, ownership, bas niveau) adresse des classes de bugs **rares dans un SaaS CRUD + domaine sur Postgres**. Les courses réelles de Cordeau (synchronisation offline, éditions concurrentes) relèvent de la conception transactionnelle et des tests, pas du compilateur.
- **Le critère le plus discriminant pour Cordeau** est probablement le **partage de règles métier avec le mobile offline-first**, où TS domine sans contestation. Viennent ensuite l'**écosystème administratif français** (facturation électronique, paiement, auth) et le coût de migration, couvert par d'autres notes.
- **Options qui captent l'essentiel du bénéfice sans migration totale** (à arbitrer, pas une recommandation définitive) :
  - (a) durcir le statu quo PHP : PHPStan 10, strict-rules, bleeding edge, interdiction des nouvelles entrées de baseline et d'ignore, Infection en CI sur le domaine, `Result` et value objects ;
  - (b) un domaine métier en TS pur partagé entre serveur et clients, avec unions discriminées, règle d'exhaustivité et éventuellement Effect pour l'orchestration ;
  - (c) un domaine Rust pour un sous-ensemble critique, exposé via UniFFI, en acceptant le coût de toolchain.

  L'option (b) est la seule qui résout le partage offline sans FFI.

### Gaps

- Aucune source ne compare directement, sur un **même SaaS métier**, la productivité et le taux de défauts d'un agent selon le langage backend. Le classement ci-dessus agrège donc des indices partiels.
- Les benchmarks par langage datent de modèles 2025 (Claude 3.7 Sonnet, Opus 4). Pour les modèles d'octobre 2026, l'écart entre langages pourrait s'être resserré ou déplacé, sans données publiques pour le dire.
- Kotlin backend (Ktor) et Gleam manquent de données d'agentic coding spécifiques. Leurs notes reposent davantage sur les propriétés du langage que sur des mesures.
