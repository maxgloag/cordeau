## Décisions de conception (et ce que le langage a imposé ou suggéré)

- **Représentation décimale : entiers à virgule fixe, à précision arbitraire (`num-bigint`)**, pas `rust_decimal` ni `i128`.
  - `rust_decimal` (mantisse 96 bits, ~7,9e28) : `checked_mul` réduit silencieusement l'échelle quand le produit déborde → perte de précision silencieuse possible sur `M × base` (remise MONTANT) dès des totaux de l'ordre de 1e13 € (une seule ligne au maximum des bornes). Rejeté.
  - `i128` en centimes : exact et `Copy`, mais `M × base / total` déborde dès ~1,3e17 € de total (≈ 13 000 lignes aux bornes max, ~2 Mo de JSON) et la remise MONTANT n'a **pas de borne supérieure** dans la spec (« 1e40 € » est une valeur valide qui doit produire `REMISE_SUPERIEURE_AU_TOTAL`). Il aurait fallu un chemin d'erreur « capacité dépassée » hors spec.
  - `BigInt` : « calculs intermédiaires exacts (décimal arbitraire) » littéralement, aucun chemin de débordement, aucun code d'erreur inventé.
  - Les grandeurs **bornées** par la spec sont typées au plus juste : `Quantite(NonZeroU32)` en millièmes (≤ 1e9), `PrixUnitaireHt(u32)` en centimes (≤ 1e9), `Pourcentage(u16)` en centièmes de % (≤ 10 000), `TauxTva` enum (pour mille). Seuls les montants calculés sont des `Montant(BigInt)` en centimes.
- **Arrondi** : une seule fonction `arrondir(num, den)` = demi éloigné de zéro (sémantique de `ROUND_HALF_UP` de Python `decimal`, l'oracle), sur une fraction entière exacte. Chaque règle de la spec est exprimée comme _une_ fraction (ex. montant ligne = `q‰ × p¢ × (10000 − r) / 10^7`), donc un seul arrondi par règle, comme exigé.
- **Division par zéro irreprésentable** : `DenominateurPositif` (constructeur `Option`), seul moyen d'appeler `arrondir`.
- Lecture du format décimal écrite à la main (`[0-9]+(\.[0-9]+)?`, ASCII strict) : `BigUint::parse_bytes` tolère `_` et `+`, il n'est appelé qu'après le contrôle.
- **Frontière « parse, don't validate »** en deux étages :
  1. `devis-cli` traduit la _forme_ JSON en `DemandeDevisBrute` (aucune règle métier) : `Saisie::{Absente, Texte, NonTexte}` (`null` → `Absente`), `LigneBrute::{NonObjet, Objet}`, `RemiseGlobaleBrute::{Absente, NonObjet, Objet}`, `lignes: Option<Vec<_>>` (absent / non tableau → `None`).
  2. `DemandeDevis::valider(&DemandeDevisBrute) -> Result<DemandeDevis, Vec<ErreurValidation>>` (domaine) applique toutes les règles et accumule les erreurs ; `DemandeDevis` a des champs privés, donc `calculer_totaux()` est une **fonction totale** (pas de `Result`, pas de cas « entrée invalide » à gérer dans le calcul).
- **Validation applicative** (accumulation d'erreurs) : chaque champ devient un `Result<T, Erreur>` indépendant, puis un `match` sur le n-uplet : tous `Ok` → valeur, sinon on collecte les `Err`. Le langage a _suggéré_ ce style (pas d'exceptions, `match` exhaustif) et il rend « toutes les erreurs détectables » quasi gratuit.
- `REMISE_SUPERIEURE_AU_TOTAL` : contrôle croisé greffé sur le `Result` de la remise, déclenché seulement si `lignes` est `Ok` (= tableau non vide sans aucune erreur indexée, `FRANCHISE_AVEC_TVA` comprise), indépendamment de `regime` et `acompte`.
- Erreurs typées : `ErreurValidation::Demande(ErreurDemande)` vs `ErreurValidation::Ligne { index, erreur: ErreurLigne }` → une erreur de ligne sans index ou une erreur globale avec index est irreprésentable. `JSON_INVALIDE` n'existe que dans l'adaptateur (le domaine ne connaît pas JSON).
- Ventilation par `BTreeMap<TauxTva, Montant>` : l'`Ord` dérivé de l'enum (déclaré dans l'ordre 0 < 5,5 < 10 < 20) donne directement le tri croissant exigé. Départage de l'écart : `max_by(base, puis taux)` explicite (ne dépend pas du comportement « dernier maximum » de `max_by`).
- Remise globale = Σ des parts (égale à M par construction pour MONTANT, Σ des arrondis par base pour POURCENTAGE) : une seule source de vérité, `Σ bases nettes = total HT net` toujours vrai.
- Sortie JSON par structs `Serialize` (ordre des clés de la spec conservé) ; code de sortie 2 réservé aux erreurs internes (écriture stdout impossible), jamais atteint en usage normal.
- `run.sh` : `exec` du binaire release (`target/release/totaux-devis`), chemin résolu depuis l'emplacement du script ; message explicite et code 2 si le binaire n'a pas été compilé.

## Auto-évaluation

**Confiance : 8,5 / 10.** Le calcul est exact par construction (entiers à précision arbitraire, un seul arrondi par règle) et chaque règle de la spec a au moins un test calculé à la main ; les risques restants sont des divergences d'**interprétation** avec l'oracle sur des entrées exotiques, pas des erreurs de calcul.

Cas ambigus / zones de doute et interprétation retenue :

1. **Trim de la désignation** : `str::trim` de Rust (blancs Unicode : espace, `\t\n\r`, NBSP U+00A0, U+3000…). Python `str.strip()` retire en plus `\x1c`–`\x1f` ; PHP `trim()` ne retire ni NBSP ni les blancs Unicode mais retire `\0`. Une désignation `" "` ou `"\x1c"` peut donc diverger entre les trois implémentations.
2. **ROUND_HALF_UP sur valeurs négatives** : implémenté « moitié loin de zéro » (sémantique Python `decimal`). En pratique aucun arrondi ne porte sur une valeur négative : exploration aléatoire (400 000 cas) sans aucune base nette négative.
3. **Écart négatif de la remise MONTANT** : appliqué littéralement, une part peut devenir négative (ex. 4 bases de 1,00, M = 0,02 → part −0,01 sur le 20 %, base nette 1,01). Testé et assumé.
4. **JSON non standard** : `NaN`/`Infinity` (acceptés par `json.loads` Python par défaut) → `JSON_INVALIDE` ici (RFC 8259). BOM UTF-8 → `JSON_INVALIDE`. Chaînes avec surrogates isolés (`"\ud800"`) → `JSON_INVALIDE` (serde_json ; Python les accepte). Imbrication > 128 niveaux → `JSON_INVALIDE` (limite de récursion serde_json).
5. **Clé magique `arbitrary_precision`** : un objet racine `{"$serde_json::private::Number": "1"}` serait lu comme un nombre → `JSON_INVALIDE` au lieu de `REGIME_INVALIDE` + `LIGNES_VIDES`. Pathologique, accepté en échange du bon traitement de `1e400`.
6. **Remise globale `{ "type": "POURCENTAGE", "valeur": null }`** : traitée comme mal formée (`REMISE_GLOBALE_INVALIDE`) — `null` n'équivaut à « absent » que pour les champs optionnels de premier niveau listés par la spec.
7. **Doublons de clés JSON** : la dernière occurrence gagne (comme Python et PHP), non testé.
8. **Stdin illisible** (erreur d'E/S) : traité comme `JSON_INVALIDE`, code 1. Erreur d'écriture sur stdout : code 2 (hors spec, inatteignable en usage normal).
9. Les codes d'erreur sont émis au plus une fois par (code, ligne) ; l'ordre de sortie est : régime, erreurs de lignes (par index), remise globale, acompte.
