## Décisions de conception (et ce que le langage a imposé ou suggéré)

- **Représentation décimale : `BcMath\Number` (PHP ≥ 8.4, extension bcmath)**. Raisons : décimal arbitraire exact, objet immuable typé (vs fonctions `bc*` sur chaînes), `round(2, RoundingMode::HalfAwayFromZero)` natif = ROUND_HALF_UP de la spec (y compris pour les négatifs, comme Python `decimal`). `brick/math` absent de `vendor/` → aurait été une dépendance externe (ADR obligatoire avec section sécurité). Les entiers natifs débordent (`quantité × prix × (100 − remise)` atteint ~10²² en unités minimales). Aucun `float` nulle part.
  - Conséquence production : bcmath n'est **pas** dans l'image Docker (FrankenPHP alpine) → `ext-bcmath` déclarée dans `composer.json` (+ hash du lock), ajoutée à `install-php-extensions` du `Dockerfile` et aux extensions de la CI. Sans cela, le code aurait planté en prod (`Class "BcMath\Number" not found`) alors que tout est vert en local — défaut qu'aucun outil du projet n'aurait signalé (phpstan connaît la classe via ses stubs).
  - Pièges du langage gérés explicitement : `new Number()` accepte `".5"`/`"5."` → regex stricte d'abord ; division **tronquée** → les seules divisions sont remplacées par `× 0.01` (exact) sauf `M × base / total`, tronqué à 10 décimales avec preuve en commentaire (pour q ≥ 0, l'arrondi demi-supérieur au centime ne dépend que de ⌊q × 1000⌋).
- **Découpage hexagonal** : `Domain/Devis` (VO `Quantite`, `PrixUnitaireHt`, `Pourcentage`, `Montant`, `Designation`, `LigneDevis`, `LignesDevis`, `BaseHt`, `RemiseGlobale` (interface) + `RemiseGlobalePourcentage` / `RemiseGlobaleMontant`, `DemandeDevis`, `VentilationTva`, `TotauxDevis`, enums `RegimeTva`, `TauxTva`, `Unite`, `TypeRemiseGlobale`, service pur `CalculateurTotauxDevis`) ; `Application/Devis` (`DemandeDevisJsonParser` + `CollecteurErreurs` + `CodeErreur` + `CalculerTotauxDevisUseCase`) ; `Presentation/Console/CalculerTotauxDevisCommand`. Les invariants métier (bornes, décimales, franchise ⇒ taux 0, remise ≤ total) vivent dans le domaine ; le parser ne fait que la lecture typée du JSON et la **collecte exhaustive** des erreurs, en déléguant chaque règle au domaine (le domaine lève, le parser traduit en code d'erreur).
- **JSON décodé en `stdClass`** (`assoc=false`) — imposé par PHP pour distinguer objet / tableau. Profondeur portée à 10 000 (défaut 512) pour ne pas refuser un JSON valide profondément imbriqué dans un champ inconnu.
- « Absent » et `null` traités de façon identique pour tous les champs (`?? null`) : conforme à la spec (obligatoire → invalide, optionnel → défaut).
- `RemiseGlobale` en interface polymorphe plutôt qu'un `if type` : `ventiler()` et `depasse()` portés par chaque forme ; la règle REMISE_SUPERIEURE_AU_TOTAL passe par `depasse()` (toujours faux pour un pourcentage).
- Trim de la désignation : « espace » = espace blanc Unicode (`\s` en mode `/u` : NBSP, espaces typographiques…), parcours linéaire (cf. sonde regex quadratique).
- Exit code 2 réservé aux erreurs internes (jamais 1, qui signifie « entrée invalide ») ; `run.sh` sort aussi en 2 si `vendor/` manque.
- Wrapper : commande Symfony via `php bin/console` (env `dev` par défaut) : ~0,11 s à chaud, ~1,2 s au premier lancement (compilation du conteneur). `php` plutôt que `symfony console` pour ne dépendre ni de Docker ni du binaire Symfony.
- Non fait, volontairement : pas d'ADR ni d'entrée THESAURUS (la spec est non normative et « ne préjuge pas de la modélisation du Devis en Phase 8 ») ; à noter que le THESAURUS anticipe `TauxTVA`/`MontantHT` (casse d'acronyme) alors que j'ai écrit `TauxTva`, `RegimeTva`, `VentilationTva` — à trancher dans l'ADR Phase 8.
